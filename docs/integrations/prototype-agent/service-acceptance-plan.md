## 1. Полный пользовательский цикл

Запустить новый прототип через обычный чат и кнопку режима прототипа. Контрольный продукт — операционный кабинет интернет-магазина. Он проверяет связанные сущности, переходы состояний, расчёты и изменения нескольких экранов одной операцией.

Контрольный запрос для нового чата:

> Создай интерактивный прототип операционного кабинета интернет-магазина на React с UI Kit. Нужны разделы «Заказы», «Склад» и «Обзор». Все данные синтетические и хранятся в памяти; прототип должен работать в одном HTML без внешних API.
>
> В заказах сделай два варианта представления: A — таблица, B — доска по статусам. Оба используют одни и те же заказы и складские остатки. Переключение A/B и разделов не сбрасывает данные. Нужны поиск по номеру заказа, фильтр по статусу, создание заказа и подробности заказа с доступными действиями.
>
> Заказ содержит позиции с количеством и ценой. Стоимость — сумма количества × цены. Статусы: «Черновик» → «Подтверждён» → «Отгружен». Черновик не резервирует товар. При подтверждении проверь все позиции: если товара недостаточно хотя бы для одной, покажи понятную ошибку с названием и доступным количеством и не меняй заказ или остатки ни по одной позиции. При успешном подтверждении зарезервируй все позиции. Подтверждённый заказ можно отгрузить или отменить. При отгрузке уменьшаются физический остаток и резерв; при отмене освобождается только резерв. Черновик можно отменить. Отгруженный или отменённый заказ нельзя снова подтвердить, отгрузить или отменить. Повторное нажатие действия не должно менять остатки второй раз.
>
> На складе покажи физический остаток, резерв и доступное количество: доступно = остаток − резерв. Количество позиции — целое число больше нуля. Повторное добавление одного товара объединяет количество в одну позицию. После подтверждения редактировать состав заказа нельзя. Все суммы и остатки пересчитываются после действий.
>
> В обзоре покажи количество заказов по статусам, сумму подтверждённых заказов и выручку по отгруженным заказам. Черновики и отменённые заказы в эти суммы не входят. Метрики отражают все заказы независимо от фильтра списка.
>
> Начальные товары: K — клавиатура, 4 000 ₽, физический остаток 10; M — мышь, 2 000 ₽, остаток 12; H — USB-хаб, 3 000 ₽, остаток 5; N — наушники, 6 000 ₽, остаток 3. Начальные заказы: Z-101 подтверждён, 2 K и 1 M; Z-102 подтверждён, 1 K; Z-103 черновик, 1 N. Начальный резерв должен следовать из этих заказов. Не добавляй другие товары или заказы.
>
> Для мобильного экрана обеспечь доступность создания заказа, просмотра позиций и всех действий. Разрушительные действия требуют подтверждения. Показывай фактический результат операции и ошибки.

## 1а. Файлы: хранение, вложения и импорт внутри прототипа

Подключение S3 обеспечивает хранение файлов/артефактов. Обработка содержимого требует отдельного пути: parser/model для обычного чата либо реализованного browser import в самом прототипе.

- Реальный S3 из локальной конфигурации: загрузка собственного маленького synthetic JSON, HEAD/проверка размера и Content-Type, чтение с полным совпадением байтов, удаление и HEAD404 — PASS. Проверка не отправляла запросы модели и не создавала chat job. Это не проверка deployed `/api/files` или чтения вложения выбранной моделью.
- В checkout `fileStrategy: s3`; обычный file path содержит upload/download стратегии. Text/context parsing может сохранять извлечённый текст отдельно, поэтому наличие S3 не означает, что любой тип файла автоматически читается моделью.

В текущих локальных изменениях добавлен путь «Загрузить как текст»: сервер сохраняет извлечённое содержимое в требования хода. После valid import выполнить экспорт и повторный импорт, сравнить каталог. CSV parser должен корректно обрабатывать кавычки/разделители в названии либо явно ограничивать поддерживаемый формат.

Текущий preview не имеет `allow-downloads`: экспорт из вложенного прототипа отмечать FAIL/BLOCKED до соответствующей целевой правки и повторной проверки. Скачивание самого HTML/ZIP кнопками чата проходит вне iframe и является другим действием. Export в самостоятельном HTML проверять отдельно. Прямой S3 доступ из прототипа отсутствует; `connect-src 'none'` запрещает сетевые запросы. Интеграция самого прототипа с backend требует отдельной реализации. Чтение ТЗ из вложения чата проверяется в этапе 1б и не зависит от импорта/экспорта внутри preview.

## 1б. Создание и доработка прототипа по ТЗ из файла — обязательный этап

Статус: реализация находится в локальных изменениях, сквозной прогон не выполнен. Перед приёмкой записать commit/digest фактически развёрнутых frontend и API, а также worker из общей подготовки. Наличие нового пути в исходниках, успешная загрузка в S3 или ответ модели «прочитал файл» не являются PASS этого этапа.

Пользовательский путь: включить режим прототипа → «Загрузить как текст» → выбрать документ → дождаться обработки → написать короткое сообщение → отправить. Непустое сообщение обязательно. Вложения поддерживаются при создании, ответе на уточнение/план/review и доработке завершённого задания. Форматы зависят от существующего parser; основной обязательный прогон — TXT/Markdown. DOCX/PDF с текстовым слоем проверять дополнительно, если они входят в заявленную конфигурацию deployment. Новое OCR и импорт/экспорт внутри прототипа в этот этап не входят.

### Контрольные документы и создание

Подготовить собственные синтетические файлы и записать SHA-256 исходных байтов:

- `prototype-spec.md`: весь контрольный запрос операционного кабинета из этапа 1, включая товары, заказы, переходы статусов и точные расчёты. Только в файл добавить требование: «Заголовок приложения — “Контур заказов FILE-SPEC-20261014”; показ контрольной метки обязателен». Не вставлять содержимое файла или метку в сообщение чата.
- `prototype-change-review.md`: «Добавь в раздел “Склад” колонку “Пополнение”. Когда доступное количество товара меньше 2, покажи текст “Нужна закупка FILE-EDIT-20261014”; иначе — “Запас достаточен”. После подтверждения, отмены и отгрузки пересчитывай колонку. Сохрани исходные товары/заказы, цены, переходы, расчёты, A/B и разделы из первоначального ТЗ».
- `prototype-change-completed.txt`: «Измени порог колонки “Пополнение” на доступное количество меньше 3. Текст предупреждения теперь “Нужна закупка FILE-AFTER-COMPLETE-20261014”. Сохрани остальные требования и исходный заголовок приложения».

Последовательность:

1. В новом чате загрузить `prototype-spec.md` через «Загрузить как текст». Дождаться завершения загрузки; проверить имя файла и пояснение, что текст включается в ТЗ. Отправить только: «Создай прототип по приложенному ТЗ».
2. До подтверждения плана проверить, что план учитывает правила заказов/резерва из документа. Если сервис задаёт уточнение, ответить штатным reply. Coding/build до подтверждения плана не начинается. В evidence записать filename/fileId и соответствующий source message/turn.
3. Подтвердить план и дождаться принятой версии. Заголовок содержит `FILE-SPEC-20261014`; начальные числа совпадают с этапом 1: доступно K = 7, M = 11, H = 5, N = 3; подтверждённые заказы = 14 000 ₽, выручка = 0 ₽. Выполнить проверки атомарного отказа, отмены и отгрузки из этапа 1. Правильная метка без работающей логики не проходит приёмку.
4. В review прикрепить `prototype-change-review.md`, отправить только: «Внеси изменения из приложенного документа». Проверить путь сохранения сообщения и `/replies`, новую принятую версию и сохранение исходного заголовка/логики. На свежем состоянии подтвердить Z-103 (1 N): доступно N = 2, колонка показывает «Запас достаточен». Создать и подтвердить ещё один заказ с 1 N: доступно N = 1, появляется `FILE-EDIT-20261014`. После его отмены доступно N = 2, предупреждение исчезает. Остальные исходные расчёты остаются верными.
5. Финализировать через штатный flow, затем в том же завершённом чате загрузить `prototype-change-completed.txt` и отправить: «Примени приложенную доработку». Проверить новый ход через submit. На свежем состоянии N = 3 — предупреждения нет; после подтверждения Z-103 доступно N = 2 — появляется `FILE-AFTER-COMPLETE-20261014`. Старый заголовок и правила заказов сохранены; предыдущие принятые HTML/ZIP и digests доступны.
6. Для проверки именно ответа на уточнение/план использовать отдельный запрос с неоднозначностью в документе, например без выбора стартового представления. Если сервис запросит уточнение, передать ответ отдельным TXT через «Загрузить как текст»; ответ в файле должен определить B как стартовое представление. Если уточнения не было, сценарий отметить NOT RUN и воспроизвести в изолированном управляемом fixture. Review reply из шага 4 не выдавать за проверку этого состояния.

### Сохранение требований и повторная доставка

- После принятия запроса оператор проверяет, что `PrototypeTurn.text` содержит короткое сообщение, имя документа и полный извлечённый текст; чат показывает исходное сообщение и ссылки на файлы. Сравнивать с результатом parser, а для TXT/Markdown — также с исходным содержимым. Отсутствуют молчаливое обрезание и двойное добавление одного fileId. В command/outbox `attachmentManifest` остаётся пустым; storage URL, ключи и credentials не попадают в требования.
- После принятия версии закрыть вкладку, открыть чат снова и отправить текстовую доработку без повторного вложения: «Добавь сортировку заказов по номеру, сохрани прежние требования». Исходный заголовок, правила и последняя файловая доработка сохраняются.
- В изолированном окружении после принятия хода удалить его исходное вложение штатным способом либо дождаться его истечения, затем перезапустить idle worker и выполнить новую текстовую доработку. Она использует сохранённые требования, не требует повторной загрузки файла и сохраняет контрольные правила. Общие S3 объекты и чужие файлы не удалять.
- Повторить принятый submit/reply с теми же messageId, Idempotency-Key и исходной revision после удаления вложения: возвращается уже принятый результат без повторного чтения файла, нового хода и повторного model dispatch. Новый запрос с новым ключом и удалённым fileId должен отклоняться. Не повторять платную операцию новым ключом для проверки идемпотентности.
- Repair/retry проверять в управляемом fixture с намеренной ошибкой сборки и согласованным бюджетом: восстановление получает исходный документ из сохранённого хода, сохраняет метки и правила, не требует доступности исходного файла. Без этого прогона гарантию чтения ТЗ при repair/retry считать непроверенной.

### Ошибки, лимиты и доступ

Ошибки и границы проверять через реальный API в изолированном окружении до платного dispatch. Права проверять также прямыми запросами, поскольку UI не позволяет выбрать чужой файл.

| Сценарий | Действие | Критерий |
| --- | --- | --- |
| Загрузка ещё идёт | Отправить через кнопку и клавиатуру до завершения обработки | Нет submit/reply/model dispatch; пользователь видит ожидание, черновик и файл сохраняются |
| Другой тип вложения | Прикрепить файл обычным provider-путём и затем включить режим прототипа; отдельно передать его fileId в API | UI требует «Загрузить как текст»; API возвращает 422 `PROTOTYPE_ATTACHMENT_INVALID` без нового хода |
| Пустое или недоступное содержимое | Пустой TXT; удалённый, истёкший, pending/failed file record; ошибка parser | Понятная ошибка загрузки либо 422 `PROTOTYPE_ATTACHMENT_INVALID` при submit/reply; нет пустой генерации, черновик сохранён |
| Количество документов | 10 разных коротких TXT и затем 11; повторить через прямой API | 10 принимаются при соблюдении общего размера; 11 отклоняются UI/API; ни один файл не игнорируется молча |
| Общая длина | Рассчитать длину сообщения + имён/разделителей + извлечённого текста; запросы на 50 000 и 50 001 символ | 50 000 принимается; 50 001 отклоняется с 422 `PROTOTYPE_REQUIREMENTS_TOO_LARGE`, без обрезания и нового хода. Проверить submit и review reply |
| Несколько документов | Передать два коротких TXT с разными контрольными требованиями; отдельно повторить один fileId в запросе | Оба текста входят в один snapshot; повторный fileId добавляется один раз |
| Чужой владелец/tenant | Второй аккаунт подставляет fileId первого; отдельный fixture другого tenant | 422 без содержимого, имени чужого документа, accepted turn или model dispatch |
| Другой чат владельца | Использовать record с явной conversationId другого собственного чата | 422 `PROTOTYPE_ATTACHMENT_INVALID`; новая загрузка без conversation binding в новом чате принимается |
| Ошибка файлового reply | Отправить reply с недоступным или слишком большим документом | Последняя принятая версия не меняется; отклонённое сообщение не остаётся в серверной истории как принятый ответ; UI сохраняет черновик/вложения и позволяет исправить запрос |

При измерении границ использовать JavaScript `String.length`, как в действующем контракте, а не размер UTF-8 файла. Для ошибки parser допустим отказ на upload до появления fileId; не требовать от всех форматов одинакового этапа отказа. DOCX/PDF нужно проверять на реальном parser: загрузка без содержательного результата не считается поддержкой формата.

Evidence этапа: хеши/имена синтетических документов, извлечённый текст или его digest, fileIds, source messageIds, снимок принятого turn без секретов, общие job/turn/revision/execution/artifact IDs, ошибки/ответы API, ожидаемые и фактические контрольные числа, расход. Учитывать прогоны этого этапа в общем согласованном бюджете раздела 5. Новые статусы — NOT RUN до выполнения, PASS/FAIL/BLOCKED после выполнения; статическая проверка реализации не заменяет сквозной прогон.

Этап считается принятым, когда создание из файла, review reply, доработка завершённого задания, продолжение без исходного файла, лимиты/ошибки/права и идемпотентность имеют PASS на указанных окружениях. Clarification/plan reply и repair/retry фиксируются отдельными результатами; непроверенные ветки остаются открытыми, а не получают PASS по аналогии.

## 2. Продолжение после паузы и перезапуска

Для этого сценария использовать отдельный прототип в состоянии review, до финализации, с сохранённой принятой версией.

| Сценарий                        | Действие                                                                                                   | PASS                                                                                       |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Reload и другая сессия браузера | Закрыть вкладку, открыть тот же чат в новой сессии, пройти авторизацию                                     | Snapshot, preview и downloads восстанавливаются; нет повторного запуска предыдущего хода   |
| Возврат на следующий день       | Открыть тот же review-прототип и запросить небольшую доработку                                             | Изменяется последний принятый source, прежние требования сохранены                         |
| Restart idle worker             | В согласованном окружении перезапустить worker между preview и доработкой                                  | После readiness новый ход завершается без зависимости от прежнего процесса/sandbox         |
| Отсутствие локального кеша      | В изолированном окружении запустить worker с новым private scratch, сохранив durable stores                | Accepted source восстанавливается из checkpoint, его digests совпадают; доработка проходит |
| Обновление только image digest  | При неизменных rules/template/toolchain pins обновить образ и повторить доработку старого review-прототипа | Существующая generation binding остаётся действительной                                    |

При изменении rules/template/toolchain pins старое задание должно получить явный ограниченный отказ по generation binding, а новый чат — работать. Переписывание immutable pins вручную не является процедурой восстановления. Очистку общего workspace/PVC для проверки не выполнять.

## 3. Отказы, отмена и повторная доставка

Начать с изолированных stores/provider fixtures и существующих integration suites. Реальные отказные прогоны потребуют согласованного окружения; их PASS нельзя заменить результатом mocked теста.

| Сценарий                               | Где воспроизводить                                                               | Ожидаемое поведение                                                                                                                                        |
| -------------------------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Отмена generation                      | Отдельное собственное задание; отмена после старта модели                        | Public state становится canceled; поздний результат не публикуется; предыдущая accepted версия доступна. Уже начатый upstream запрос может иметь стоимость |
| Отмена build                           | Отдельное задание после gateway.session_started                                  | Fencing запрещает позднюю publication; cleanup outcome фиксируется отдельно; новые полномочия старому execution не выдаются                                |
| Неуспешная доработка                   | Provider fixture выдаёт invalid TSX или фиксированный build error                | Последняя accepted версия/downloads сохраняются; пользователь видит ошибку; repair ограничен фактической policy и бюджетом                                 |
| Недоступный model provider             | Fixture: 429, timeout, разрыв после отправки                                     | Ограниченный отказ с понятной причиной; неизвестный outcome учитывается; тот же платный запрос не повторяется вслепую                                      |
| Отсутствующий build image              | Отдельный fixture/acceptance lock с заведомо недоступным digest                  | Причина pull/start диагностируется; задание приходит к видимому ограниченному исходу или recovery state; нет бесконечной обычной обработки одной команды   |
| Потеря ответа Gateway create/session   | Изолированный transport fixture                                                  | Durable intent предотвращает второй create/session; состояние требует reconcile/quarantine и отражено пользователю/оператору                               |
| S3 недоступен после build              | Изолированный storage fixture                                                    | Неполная версия не становится current; verified output/cleanup debt сохраняются по контракту, старые accepted артефакты не заменяются                      |
| Повторный submit/approve/reply         | Повторить тот же запрос с тем же Idempotency-Key; отдельно — устаревшую revision | Одна логическая операция/доработка; stale request отклонён; нет второй publication и повторного model dispatch той же операции                             |
| Worker crash до/после completion и ACK | Изолированный worker/stores, отдельно для каждой границы                         | Уже принятый outcome не применяется повторно; uncertain execution не запускается заново без reconciliation; нет потери принятого результата                |
| Два собственных чата                   | Проверить разрешённую concurrency и превышение фактической configured quota      | Результаты не смешиваются; очередь/отказ видимы; quota освобождается согласно подтверждённому состоянию                                                    |

Особое внимание: в текущем `local-react-stages.js` build failure с `writersStopped !== true` выбрасывается без обычного `failure.json`, а `GatewayPipelineClient` запрещает replay существующего execution через `GATEWAY_EXECUTION_RECOVERY_REQUIRED`. Поэтому bounded failure/recovery — открытый критерий приёмки, который может потребовать исправления. Успех generation и последующей доработки эту ветку не проверяет.

## 4. Права и независимость обычного чата

- Второй тестовый аккаунт пытается прочитать snapshot, SSE, HTML, ZIP и выполнить mutation задания первого аккаунта: всё отклоняется без раскрытия данных. Смена conversationId тем же владельцем также отклоняется. Проверять API, а не только отсутствие кнопки в UI.
- Переподключить SSE/вкладку во время операции: snapshot согласован с durable cursor, assistant projection и принятая версия не дублируются.
- В согласованном окружении выключить только worker/intake. Возможность новой генерации должна исчезнуть по heartbeat TTL; ordinary login/chat работают, набранный draft сохранён и сам не отправлен как обычное сообщение. Принятые downloads и cancel доступны.
- Вернуть worker: capability появляется после проверки readiness/heartbeat; новый собственный прототип проходит основной сценарий. Не считать Gateway GET или `/healthz` единственным доказательством полной генерации.

## 5. Повторяемость и эксплуатация

Предлагаемый стартовый объём: пять новых прототипов с одним контролируемым запросом, по две доработки для трёх из них, две финализации/экспорта, один отдельный cancel и один idle restart-before-edit. Количество прогонов согласовать с бюджетом; массовые генерации автоматически не запускать.

Записывать success/failure, время ожидания/планирования/generation/build/publication и provider usage отдельно. На пяти прогонах нельзя заявлять статистический SLA; сравнивать наблюдения и искать повторяющиеся ошибки. Пороги latency согласовать до замеров с учётом выбранной модели.

Для проверки времени жизни образа выполнить сценарий отсутствующего image без ожидания 72 часов. Отдельно зафиксировать operator retention policy и процедуру пересборки/rollout embedded release lock. Публикация image сама по себе не обновляет running worker. Старые HTML/ZIP должны оставаться доступны независимо от удаления build image.

Для длительного наблюдения предложить отдельный согласованный период: readiness, heartbeat outages, pending commands, повторения failed/recovery codes, sandbox cleanup debt, model budget receipts, размер scratch и durable storage. Наблюдение не должно создавать платные генерации на каждом опросе. Этот план не создаёт расписание/монитор автоматически.

## Критерий результата

- Основной UI цикл и restore-after-idle/reload выполнены с evidence на выбранном deployment.
- Этап 1б чтения ТЗ из файла выполнен с отдельным evidence; создание и файловые доработки работают, сохранённый текст переживает удаление исходного вложения, ошибки/лимиты/права и повторная доставка подтверждены. Непроверенные clarification/plan и repair/retry ветки перечислены явно.
- Export/offline functionality и owner/conversation denial подтверждены.
- Cancel, unavailable worker и bounded failure/recovery подтверждены в указанном для каждого сценария окружении.
- Нет повторной publication, слепого replay неизвестного paid outcome или зависания без видимого recovery/failure результата.
- Все обязательные сценарии имеют PASS; FAIL и BLOCKED перечислены с reproduction, владельцем и следующим действием. Успешный основной сценарий при FAIL recovery означает, что требуется доработка надёжности сервиса.

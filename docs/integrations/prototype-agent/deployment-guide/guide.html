Суть запускаРазворачиваем отдельный исполнитель задач — worker. Он работает рядом с API ChatRouter и использует уже существующие БД, очередь, хранилище файлов и Gateway. Новый публичный адрес worker не нужен.

Два режима — разная степень готовности

Текущий режим

Worker + сборка в Gateway

Worker обращается к выбранной модели и передаёт подготовленный код в Gateway для сборки.

direct-react-v1

Контейнер и конфигурация подготовлены. Полный production-путь пользователя ещё предстоит принять.

Следующий этап

OpenCode внутри Gateway

Агент пишет код в sandbox и вызывает модель только через Model Proxy в API.

release-lock.agent = null

Сетевая изоляция Gateway не принята. Этот режим текущим запуском не включается.

03 · кнопки в GitLab

Порядок deployment

Кнопки worker доступны в MR в main и на main. Обычный pipeline не ждёт их ручного запуска.

1

Подготовить нужную версию и Secrets

Убедиться, что изменения есть в GitLab pipeline. Оператор заранее создаёт prototype-worker-env, сверяет API Secret, БД и ключи. Значения не вставлять в Git/CI log.

2

Обновить ChatRouter API

Существующий путь: build → deploy_GK_prod. Нужны backend guards и worker routes. Порядок Задача API определяется текущим pipeline; это не новая manual-кнопка worker.

3

Проверить настройки API

prototypeAgent.enabled=true, PROTOTYPE_TRANSPORT_ENABLED=true, auth bearer; OPENROUTER_API_URL — корпоративный provider. Для adapter: PROTOTYPE_MODEL_PROXY_ENABLED=true, RSA key только API.

4

Нажать build_prototype_worker

Job собирает отдельный image и передаёт deploy его точный digest. Artifact хранится 7 дней; после истечения надо пересобрать.

5

Сначала развернуть без обработки задач

В форме manual deploy_prototype_worker явно задать WORKER_INTAKE_ENABLED=false. Процесс проверяет зависимости и не запускает генерации.

6

Проверить режим ожидания

/healthz → 200; application /readyz → 503 ожидаем. В режиме ожидания chart использует healthz для готовности pod, поэтому Задача CI может быть успешным.

7

Включить контролируемый пилот

Повторить deploy с WORKER_INTAKE_ENABLED=true. После проверок Redis/OBS worker сообщает API готовность; /readyz → 200. Текущий лимит — до $2 на один ход прототипа.

8

Пройти пользовательский цикл

Один разрешённый аккаунт и согласованная модель: план, подтверждение, preview, правка, итог, скачивание. Проверить стоимость и отмену.

Сейчас по умолчанию обработка включенаВ worker values и CI стоит true. Без явного false deploy включает приём задач и может вызвать платные обращения. Перед включением обработки согласовать объём пилота и стоимость.

Где: namespace openrouter-chat, release prototype-worker; values envs/prod-prototype-worker.yaml; chart helm/prototype-service. Job создаёт Secret для скачивания image, но не рабочий env Secret. При ошибке активного запуска Helm выполняет откат; это не удаляет данные задачи.

Один источник,
разные получатели

Одинаковые значения у API и worker допустимы.
Две независимые ручные копии — источник ошибок.

Где найденоЧто это и что с ним делать
.env в корнеНастройки локальной разработки. Локальный worker читает этот файл. Отдельного .env внутри apps/prototype-service сейчас нет.
.prototype-dev/runtime.jsonАвтоматическая запись для связи локальных API/worker. Повторяет Redis/БД прототипов и содержит временную identity. Не редактировать как конфигурацию; в production не переносить.
.prototype-dev/production-identity/
adapter-secrets.env		Защищённый файл проверки production через SSH-туннель. Это отдельное окружение. Не объединять с локальным .env и не копировать в pod.
worker.production.example.envШаблон имён и placeholders. Здесь нет настоящих секретов. На его основе оператор готовит worker Secret.

Правильная схема production

Управляемое хранилище DevOps → два ограниченных набораAPI получает librechat-secret-env. Worker получает prototype-worker-env. Общие значения выдаются из одного источника и обновляются согласованно; полный API Secret worker не передаётся.

Как вынести значения без поломки

  1. Сохранить актуальные значения в защищённом production источнике.
  2. Проверить, что API и worker получают нужные одинаковые поля.
  3. Убрать значения из YAML в Git и проверить запуск и расшифровку существующего ключа модели.
  4. Если значения в Git действующие, оператор оценивает доступ и планирует безопасную замену ключей. Она выполняется отдельно от переноса.
CREDS_KEY / CREDS_IV нельзя просто заменитьИми зашифрованы сохранённые ключи доступа к модели. Для замены нужен план расшифровки старых записей и миграции. Смена JWT keys также может завершить пользовательские сессии.

В этой работе секреты не переносились и не менялись. Файлы и текущие процессы сохранены. В PDF присутствуют только имена переменных.

Минимальный список worker Secret

MONGO_URI, PROTOTYPE_MONGO_URI, REDIS_URI, SANDBOX_GATEWAY_URL/TOKEN, PROTOTYPE_SERVICE_TOKEN, OPENROUTER_API_URL, CREDS_KEY/IV, AWS_BUCKET_NAME, AWS_REGION, AWS_ENDPOINT_URL, AWS_FORCE_PATH_STYLE, AWS_ACCESS_KEY_ID/SECRET_ACCESS_KEY.

Адреса, bucket, region и флаги — настройки, не всегда секреты. Пароли и ключи оператор хранит защищённо. Реальные значения берутся из существующей среды, а не из примера PDF.

RSA подпись — один источник на APIPROTOTYPE_MODEL_TOKEN_PRIVATE_KEY_BASE64 или PROTOTYPE_MODEL_TOKEN_PRIVATE_KEY_PATH, не оба одновременно. Будущий agent получает короткий токен задачи, а не RSA private key.

Как запускается процесс

# Production: настройки уже переданы кластером
node apps/prototype-service/src/entrypoint.js

# Development: читает корневой .env
npm run prototype:dev

Production entrypoint не загружает корневой .env. Image не должен содержать root env/файлы секретов для проверок. Если нет роли или обязательного поля, при запуске будет указано имя отсутствующей настройки.

06 · пользовательский путь

От запроса до прототипа

Всё происходит в обычном чате.
Worker и сборка работают за карточкой задачи.

Если worker недоступен

Новая генерация не начинается. Обычный чат работает; сохранённые результаты доступны, свои задачи можно отменить.

Если нет ключа или средств

Исправить доступ/баланс и продолжить через разрешённое действие. Не создавать скрытых автоматических повторов.

Подготовка и уточнения могут обращаться к платной модели ещё до подтверждения плана. Показывать фактическую стоимость; не считать её нулевой только потому, что сборка ещё не началась.

07 · приёмка и остановка

Когда запуск можно считать успешным

Процесс готов

  • При обработке задач: /readyz → 200.
  • API получает свежие сообщения готовности worker.
  • Очередь/OBS/prototype Mongo работают.
  • Секретов в log/архивах нет.

Пользовательский цикл принят

  • Инструмент виден только нужному аккаунту.
  • План, preview, правка и скачивание работают.
  • Стоимость и cancel проверены.
  • Обычный чат работает при сбое.

Как остановить новые генерации

  1. Отключить prototypeAgent/transport на API.
  2. Развернуть worker с WORKER_INTAKE_ENABLED=false.
  3. Сверить активные задачи и закончить только собственные удалённые sessions. Не удалять Mongo, OBS и Secrets.

Остановка worker не доказывает отмену уже запущенного Gateway sandbox. Если результат операции неизвестен, сначала проверить её состояние; не повторять автоматически оплачиваемое действие.

Что ещё нужно для OpenCode

Gateway должен принять отдельную изоляцию агента9 октября session запускалась под root вопреки USER образа; provider и посторонний интернет были доступны. Наш launcher исправляет UID только нашего процесса. Платформе нужен запуск от обычного пользователя и запрет лишних сетевых направлений.

После исправления сети повторить проверки, принять короткие токены, потоковые ответы, инструменты и учёт стоимости и работу установленного OpenCode с исходниками. Только после этого закрепить принятый образ агента. Для Storybook 8 октября корпоративный endpoint давал 307 на себя; legacy тогда прошёл. Разрешать выбранный MCP origin отдельным согласованным исключением.
